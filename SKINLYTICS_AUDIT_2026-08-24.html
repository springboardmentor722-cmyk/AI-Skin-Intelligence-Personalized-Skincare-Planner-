Read-only architecture & requirements audit

Is Skinlytics aligned with its own spec?

Audited against docs/ARCHITECTURE.md (the real, current architecture reference — no architecture.md exists at repo root) and the 15-page requirements PDF (no skin_same.pdf exists at repo root either — this is the only requirements PDF in the repo). Five parallel code audits, cross-checked against both documents line by line.

Overall: Mostly complete 11 / 12 PDF modules substantially delivered 1 architecture rule violated 1 doc self-contradiction (audit logging)

Bottom line

Every one of the PDF's 12 modules has a real backend service behind it — no module is a frontend-only mockup. The two things a diligent reviewer should not accept without a decision from you: (1) docs/ARCHITECTURE.md §9 promises a clinical-data access audit trail that does not exist in code (§2, elsewhere in the same doc, correctly says it doesn't) — this is a live compliance question for a health-data app, not a nice-to-have; (2) the Admin service writes directly into Consultant/Dermatologist profile tables it doesn't own, with no sanctioned interface to call instead — a real, unambiguous violation of this repo's own single-writer rule.

Everything else found is real but smaller: Excel export was never built (PDF asks for PDF and Excel), only Google OAuth is wired (PDF says "OAuth2 login," ARCHITECTURE.md says Google/Facebook/Apple), one profile field (dermatologist consultation modes) can never be set so a validation check silently no-ops, six minor index/nullability drifts between the live migrations and the canonical schema doc, and the frontend CI pipeline runs zero tests despite 25 Playwright specs and 3 unit-test files existing on disk. None of these break the running system today; all of them are worth fixing before calling the project done.

D

Architecture audit

Where the code follows docs/ARCHITECTURE.md, where it deviates, and which deviations are real debt vs. acceptable, documented calls.

Matches

14-service modular monolith under backend/app/services/, all routes under /api/v1, single auth location (core/security.py), Better Auth identity tables never touched by Alembic (confirmed, zero violations), Alembic chain is a clean single linear head with no branches or orphans (8f3c1a6d9e42), scoring_weights CHECK constraint present and DB-driven, not hardcoded.

Real deviations

Admin bypasses the single-writer rule
admin/service.py:124,125,129,131 · ADR-005

Directly mutates ConsultantProfile/DermatologistProfile ORM models it imports rather than calling those services' own interfaces — and no write interface exists there to call. No functional bug (writes succeed, get audit-logged at the admin layer) but an unambiguous rule violation this repo's own docs call "bugs, not style choices."

Read-only cross-service model access, never formalized
ingredients, recommendations, skin_profile, appointments, clinical_review

Each imports another service's ORM model directly for read-only joins on reference/catalog data. Self-documented in code comments as a deliberate, consistent pattern — but AGENTS.md requires a new structural pattern to get an ADR, and none exists.

No edge-level (middleware.ts) role guard
web/ — client-side layout checks only

Not a live vulnerability: every backend endpoint independently re-checks role + ownership (confirmed by the security audit, no counter-example found). It is a single point of failure if a future endpoint ever ships without its dependency.

Documentation vs. reality

docs/ARCHITECTURE.md §4 claims the Notification and Report services are "still to be built in M3–M4." Both are real: full CRUD, wired into main.py, covered by test_notifications_service.py / test_reports_service.py. Timestamps confirm the doc simply predates these services and was never updated — code is ahead of docs here, the reverse of AGENTS.md's usual "code is the bug" default.

Separately, §2 and §9 of the same document flatly disagree on whether clinical reads are audit-logged (resolved below, §E doesn't cover this — see the callout in the Executive Summary and item #14 in the matrix). This is the one finding in the whole audit that isn't a "which is right" question — it's a genuine open product decision.

F

UI/UX audit

No screens redesigned here — only checked against the PDF's dashboard requirements and this repo's own locked design system.

What's solid

Both themes fully implemented (full .dark token block, not partial; next-themes, server-persisted). Loading/error/empty states consistently present across every page spot-checked, via a shared widget-state.ts helper. Skin Score Ring (the locked signature element) renders the real 5 weighted mini-bars everywhere it appears. Reports export exists and works — for PDF.

Gaps found

Reports UI has no format selector at all — ReportGenerateRequest carries no "format" field, so Excel isn't just unbuilt on the backend, the frontend never offered it either. /admin/system-reports is nav-flagged as finished but is 100% placeholder. Two clinical dashboards show a static "tip" banner beside live data with no "sample" disclosure, unlike Admin's honestly-badged fixtures.

G

Testing audit

Backend tests

Every one of the 14 named services, plus notifications, reports, and analytics, has a dedicated test file — no service is untested. Depth varies: scores (60 tests, incl. a randomized property test) and clinical_review (33 tests, an "unassigned user rejected" negative test on nearly every read path) are the strongest. weather is the thinnest — 3 tests, no router-level test at all. appointments is the newest and most exhaustive, including a real concurrent-booking race-condition test.

Frontend tests

3 unit-test files (assessment payload builder, severity bands, widget utils) and 25 Playwright e2e specs covering every role, onboarding, RBAC negatives, theme persistence, and a real Postgres/Mongo/worker restart-persistence check. No spec exists for the appointment/consultation flow — the one feature with zero e2e coverage despite full backend coverage.

Integration / CI reality

backend-ci.yml: ruff, ruff format, mypy --strict, and the entire pytest suite against real Postgres/Redis/Mongo — nothing skipped. frontend-ci.yml: tsc, eslint, and build — zero test execution, unit or e2e. e2e-ci.yml: runs a curated 6 of the 25 Playwright specs plus 2 visual-regression checks; the other 19 (including onboarding, admin RBAC, reports, reminders) exist and pass locally but never gate CI.

Real HTTP / browser verification

The appointment feature was independently verified this session with 47/47 real HTTP assertions against a live dev stack, and walked through in a real Chrome browser across all 3 roles (user, consultant, dermatologist). Both are one-time manual verifications from this session, not committed, automated, or repeatable — they don't substitute for the missing Playwright spec above.

Prioritized pending list

🔴 Critical

Must resolve before "complete"

Clinical-data read access has no audit trail
Source: ARCHITECTURE.md §9 (self-contradicted by §2) · Affects: Consultant, Dermatologist, Admin

Why pending: §9 states every consultant/dermatologist/admin read of a user's skin data writes an immutable audit row — "health data demands an access trail." Verified: zero write_audit_log calls exist on any read path anywhere in the backend; only mutations are logged.

Files: clinical_review/service.py (10 read functions, 0 audit calls) · admin/service.py (write_audit_log, the only real call sites) · Recommended: either implement read-audit-logging, or correct §9 to match §2 and the real code — this is a decision for you, not something to silently pick.

Admin writes into tables it doesn't own
Source: ADR-005, AGENTS.md §2 rule 4 · Affects: Admin, Consultant, Dermatologist (profile data)

Why pending: admin/service.py imports and directly mutates ConsultantProfile/DermatologistProfile ORM models. No write interface exists on the owning services to call instead — this isn't a shortcut around one, it's a genuine missing seam.

Files: backend/app/services/admin/service.py:124,125,129,131 · Recommended: add verification-status write functions to consultant_profile/service.py and dermatologist_profile/service.py; have admin call those.

🟠 Important

Real gaps, not blocking the core system

Excel export was never built
Source: PDF §4.11 · Affects: User, Consultant, Dermatologist

Why: PDF explicitly requires "PDF export" and "Excel export." Only PDF exists (reportlab); zero references to openpyxl/xlsx anywhere in the backend, and the frontend request shape has no format field to select it with.

Files: backend/app/services/reports/service.py · Recommended: add an xlsx path (openpyxl) alongside the existing PDF builder.

Dermatologist consultation-mode validation silently no-ops
Source: schema gap · Affects: Dermatologist

Why: DermatologistProfileSubmit/Update have no consultation_modes field, so the column is always NULL. Booking's validation (if consultation_modes and ...) short-circuits to "skip check" on NULL — bookings aren't rejected, but the feature is asymmetric: consultants get real mode validation, dermatologists get none.

Files: backend/app/services/dermatologist_profile/schemas.py (add field, mirror consultant_profile/schemas.py:29,51,73) · appointments/service.py:206-236

frontend-ci.yml runs zero tests
Source: AGENTS.md §7 ("quality gates pass") · Affects: whole frontend

Why: The workflow runs tsc, eslint, and build — never npm run test:unit (3 files) or any Playwright spec. AGENTS.md's own definition-of-done claims frontend quality gates are enforced; they aren't, for tests specifically.

Files: .github/workflows/frontend-ci.yml · Recommended: add a test:unit step; consider widening e2e-ci.yml's curated 6-spec subset.

No e2e test for the appointment/consultation flow
Source: test-coverage gap · Affects: User, Consultant, Dermatologist

Why: Full backend coverage exists (91+28 tests) but zero Playwright specs reference "appointment." This session's 47/47 HTTP checks and 3-role browser walkthrough were manual and one-off, not committed.

Files: web/tests/e2e/ (new file) · Recommended: book → confirm → set meeting link → user sees it, mirroring the backend test's shape.

19 of 25 Playwright specs never run in any CI workflow
Source: CI audit · Affects: whole frontend

Why: Real, passing local tests (onboarding, admin RBAC, reports, reminders, ingredient intelligence, persistence-after-restart) provide zero regression protection today.

Files: .github/workflows/e2e-ci.yml

appointments.cancelled_by is write-only
Source: DB/API audit · Affects: User, Consultant, Dermatologist

Why: Set on every cancellation, never returned — neither party can ever see who cancelled an appointment even though the data already exists.

Files: appointments/schemas.py:67-82 (add to AppointmentRead)

product_ingredients indexes documented but never migrated
Source: DB/API audit · Affects: recommendations, ingredients (query cost)

Why: v3.sql declares idx_product_ingredients_product/_ingredient; the migration whose own docstring claims to mirror v3.sql exactly never creates either. Real, uncompensated query cost on a join table.

Files: new Alembic migration; backend/app/migrations/versions/ccb49f9b0f47

docs/ARCHITECTURE.md's module map is stale
