# Schema changes — v2 → v3

Why v3 exists: adopting **Better Auth** (ADR-002) means identity is owned by Better Auth
with **string user IDs** (ADR-003). That single decision ripples through every store.

## What changed
| Store | v2 | v3 |
|---|---|---|
| PostgreSQL | serial-integer `users` + custom `oauth_accounts` + `roles` table; `user_id INTEGER` FKs | Better-Auth `user`/`session`/`account`/`verification`/`jwks` (string ids); role on `user.role`; **all `user_id`/`consultant_id` FKs are `TEXT REFERENCES "user"(id)`** |
| MongoDB | `user_id: Integer` | `user_id: String` (all collections) |
| Elasticsearch | `user_search_logs_index.user_id: integer` | change to `keyword` (string). Product/ingredient/article indexes unchanged |
| Vector DB | `user_{id}` metadata implicitly int | `user_id` metadata is a string; ids already string-formatted |
| Redis | `{user_id}` in keys | unchanged (keys were already strings) |
| Infrastructure (Redis/S3) | — | unchanged from v2 |

## Migration note
Identity tables (`user`, `session`, `account`, `verification`, `jwks`) are generated by the
Better Auth CLI (`npx @better-auth/cli generate`) — keep that migration stream separate from
Alembic. Alembic owns only the domain tables. Since we're pre-deployment (Milestone 1), just
create fresh from v3 rather than writing INTEGER→TEXT ALTERs.

Everything else (skin taxonomy, ingredients + junctions, routines/products, scoring,
progress, consulting, notifications/billing, indexes, seeds) is identical to v2 apart from
the id type of user references.
