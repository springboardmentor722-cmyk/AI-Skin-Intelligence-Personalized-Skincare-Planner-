## 1. Why the CLI died

Three things compounded:

1. **`.git/index.lock` was left behind** (0 bytes, 17:18). Every subsequent git write failed with *"Another git process seems to be running."*
2. **`.claude/settings.json` ran `graphify.EXE hook-guard` as a `PreToolUse` hook on every `Bash`, `Grep`, `Read`, and `Glob` call** — so the guard fired on literally every tool invocation.
3. **The graph it guards had been deleted mid-rebuild.** `graphify-out/` held chunks 02–11 with no chunk 01 and no final `graph.json` / `GRAPH_REPORT.md` / `manifest.json`. The rebuild started 16:37 and never finished.

On top of that, `git filter-branch` had rewritten `dev` (reflog `HEAD@{1}: filter-branch: rewrite`) to purge `graphify-out` from history, followed by `a01d821 chore: remove graphify-out graph artifacts`.

**Damage assessment:** none permanent. `origin/dev` was never touched — local `dev` was 47 commits ahead, 0 behind. The pre-rewrite backup is still at `refs/original/refs/heads/dev` → `9e09a9c` if you ever want it. Per your decision, the rewrite stands.

### What I changed to unblock it

| Action | Restore with |
|---|---|
| Removed `.git/index.lock` | n/a |
| `.claude/settings.json` hooks emptied | `cp .claude/settings.json.graphify-hooks.bak .claude/settings.json` |
| `.git/hooks/post-commit` + `post-checkout` disabled | rename `*.graphify.disabled` back |
| Deleted partial `.graphify_chunk_*.json`, `.graphify_ast.json`, `.graphify_detect.json` | regenerated by `graphify .` |

The git hooks rebuilt the graph **on every commit**, which is what generated the churn that motivated the history rewrite in the first place. I'd leave them off and run `graphify .` by hand.

## 2. Line endings — the 594-file problem is gone

`git status` reported **594 modified files / 283,293 insertions / 282,635 deletions**. Filtered for real content, it was **19 files**. Everything else was CRLF vs LF: `.gitattributes` had no text policy and `core.autocrlf` was unset, so a Windows checkout rewrote every tracked text file.

Fixed in `f95cfdf`:

- `.gitattributes` now declares `* text=auto eol=lf`, with explicit `eol=crlf` for `.bat`/`.cmd`/`.ps1` and `binary` for images, fonts, Office files, and model weights.
- `core.autocrlf=input` set locally, so commits normalise on the way in.
- One casualty found and repaired: `web/designs/wireframes/source/images/app-products/img_000_493f5560.jpg` had been treated as text and had already gained 11 bytes of CR padding in the worktree. Now declared binary and restored to its HEAD content.
- `graphify-out/` is ignored wholesale, matching `a01d821`.

**`git status` is now clean.** P14's own "confirmed `git status` is clean" exit condition is reachable for the first time.

## 3. Defects found and fixed (`43edab4`)

### 3.1 Unbounded N+1 on the clinical dashboard's main endpoint — the big one

`clinical_review.get_portfolio_stats` is deliberately unpaginated ("across the professional's WHOLE active roster") but looped two queries per client:

```python
for user_id in user_ids:
    name, _email = await _get_user_row(db, user_id)                        # 1 query
    scores = await scores_service.get_recent_scores(db, user_id, days=90)  # 1 query
```

That's **5 + 2N sequential round trips**, growing with every client a professional takes on, on the endpoint that renders every KPI, donut, bar, trend, and stat-footer cell of the clinical dashboard.

Worth noting the sibling function `list_my_clients` has the *same* pattern with a docstring that names it explicitly — *"a real N+1 whose blast radius scales with a professional's entire client count"* — and bounds it with SQL-level `LIMIT`/`OFFSET`. The P14 function reproduced the pattern with no bound at all.

Now **a constant 7 queries**, with the loop reduced to in-memory aggregation. Three new/extended interface functions, all following the existing `*_for_users` convention in `skin_profile/service.py`:

- `scores.get_recent_scores_for_users(db, user_ids, days)` — new bulk sibling
- `routines.list_active_step_counts_by_user(db, user_ids=None)` — optional cohort filter. It was previously loading a row for **every user on the platform** into a dict purely to test membership of one professional's roster. Analytics genuinely wants everyone and still calls it unfiltered.
- `clinical_review._get_user_rows(db, user_ids)` — bulk sibling of `_get_user_row`

### 3.2 A deleted user row 500'd the entire clinical dashboard

`_get_user_row` calls `.one()`, which raises when the row is absent. Correct for `get_client_detail` — a request for one named client who no longer exists should fail loudly. Wrong for a portfolio aggregate: a single client whose Better Auth row was deleted while the `consultant_clients` assignment survived took down every KPI on the page. The bulk version omits missing ids and the caller falls back.

### 3.3 `portfolio_score_trend` averaged across a shrinking sample

The series is keyed by assessment ordinal, and the frontend labels it honestly ("Assessment 1", "Assessment 2"…). But the sample size shrinks as the index grows: if one client has 30 assessments and everyone else has 3, **index 29 is one client's score rendered identically to index 0's full-cohort average**. A clinician reads a rising tail as "my clients are improving" when it's a single outlier with more history.

Now truncated at the first index where fewer than half the scoring clients contributed, so every plotted point is representative.

### 3.4 Failed requests rendered as "Nothing here yet"

Eight of nine user-dashboard widgets used:

```tsx
state={q.isLoading ? "loading" : isEmpty ? "empty" : "ready"}
```

No `isError` branch — so a 500 told the user they had no data, and offered no retry. Directly against P14's guardrail: *"every fetch has loading, empty, and error states wired with a retry path"* and *"No screen may render a blank card on failure."* The P3 widget kit already supported `state="error"`; it simply wasn't wired.

- New `web/lib/widget-state.ts` — `widgetStateFor(query, isEmpty)` and `retryFor(query)`, so the precedence (loading > error > empty) is decided once instead of re-derived per widget.
- `WidgetError` gained an optional `onRetry`, threaded through all 13 widgets.
- User, admin, and clinical dashboards all wired to it.

The clinical dashboard was already handling `isError` correctly — it only lacked the retry path.

### 3.5 The hydration goal disagreed with the score

The dashboard graded water intake against a hardcoded **2.5 L**:

```tsx
computePercent(latestLifestyleLog.water_intake_liters, 2.5)
// label: `${hydrationPercent}% of 2.5L goal`
```

while the scoring engine uses `HYDRATION_BENCHMARK_LITERS = 3.0` (ADR-021 C3 / ADR-028 corrected it from 2.0 at P10). A user drinking 2.5 L saw **"100% of 2.5L goal"** on a card sitting next to a Skin Score whose H sub-score was **83**. Two numbers for the same thing on the same screen — and 2.5 matched neither the old benchmark nor the new one.

Single frontend constant now, in `score-components.ts`, documented as needing to track the backend one. The durable fix is for the API to publish the benchmark alongside the score; noted in the constant's docstring.

### Tests added

- `get_recent_scores_for_users`: equivalence with the per-user call it replaced (same rows, same ascending order), plus every-requested-user-present and empty-input short-circuit.
- `list_active_step_counts_by_user`: cohort filtering, and the `None` (all users) vs `[]` (empty cohort) distinction — the exact bug an `if user_ids:` guard would have introduced.

## 5. Still open — good candidates for the CLI agents

Carried over from the pre-crash review pass (that report was written to
`M2_EXTERNAL_REVIEW_P14.md` but was untracked when the CLI session ended, so it
did not survive — the findings are restated here in full):

1. **Overlapping concern cards double-count severity.** `skin-concerns.json` ships both "Fine Lines & Wrinkles" *and* "Fine Lines", and both "Dark Spots & Pigmentation" *and* "Dark Marks". `_skin_condition_score` sums deductions per concern independently, so tapping both fine-lines cards at severity 8 costs **30 points** for one condition. Faithful to the docx, still a silent corruption of the headline score. Fix: a `synonym_group` key plus max-severity-per-group collapsing.
2. **The condition sub-score floors at zero.** Seven high-severity concerns → `100 − 105` → clamped to 0. Everyone past that point scores identically, so the metric stops discriminating exactly where it matters most. Needs a saturating curve, an ADR (next free number is **ADR-034**), and an `AI_ML.md` update.
3. **The admin dashboard still shows five fabricated business metrics** (revenue ₹24,80,500, 99.9% uptime, 125,430 page views) with no visual distinction from the live-queried cards beside them. ADR-023 documents why each is a fixture, but the admin looking at the screen can't tell.
4. **The visual-regression CI step can't fail** — `set +e`, `--max-pct 8`, `exit 0`. ADR-031's reasoning is sound, but the anti-drift purpose the P13 spec named is unprotected. Suggested: keep the source-PNG comparison report-only, add a hard build-to-baseline gate at `--max-pct 2`.
5. **`PROGRESS.md` has no `M2-P*` entries at all** (1 incidental hit), against DoD rule 7. Its closing paragraph still reads *"The natural next feature milestone is M2."* It's also 3,914 lines / 295 KB.
6. **`M2_TASK_LEDGER.md` rows P1–P6 still say `TODO`** despite those phases being merged.

Items 1 and 3 are small and belong in M2. Items 2, 4, 5, 6 are reasonable openers for the CLI to take with `/superpowers:writing-plans`.

## 6. Restoring your CLI setup

Before re-enabling the graphify hooks, rebuild the graph once by hand so the guard has something to guard:

```bash
graphify .
```

Then, if you want the hooks back:

```bash
cp .claude/settings.json.graphify-hooks.bak .claude/settings.json
mv .git/hooks/post-commit.graphify.disabled  .git/hooks/post-commit
mv .git/hooks/post-checkout.graphify.disabled .git/hooks/post-checkout
```

I'd reconsider the post-commit one specifically — rebuilding a knowledge graph on every commit is what produced the churn that led to the history rewrite. A manual `graphify .` after a phase merge gets you the same benefit without the write amplification, and `graphify-out/` is now gitignored so it stays local either way.
